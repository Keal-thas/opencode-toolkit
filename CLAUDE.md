# Working notes for this repo

See README.md for what the project does and its current status/open items, and TODO.md for concrete follow-up work still to be done. This file is about *how* to work on it.

## Preferences

Single-person project used across multiple machines/environments (this Mac, the Windows target machine, wherever it's cloned next) — these preferences are git-tracked here, instead of living only in a Claude Code memory file tied to one machine/account, specifically so they hold regardless of which environment a session is running in.

- **Deliver anything needing confirmation or unhurried reading as a file, not a chat wall of text.** Keep the chat reply itself to one or two sentences: the headline plus a pointer to the file. Attention is limited and chat output doesn't get read exhaustively. This repo uses a gitignored `.local/` directory at the repo root for exactly this (scratch notes, session summaries, pending-decision write-ups); clean up a `.local/` file once its content has actually been acted on, don't let it accumulate.
- **Verify claims against the real system when the tooling exists, rather than reasoning from inspection alone.** Has caught real bugs: a `.json`/`.jsonc` false alarm, `module-analysis`'s silent `explore`→`build` fallback, a `docker-compose.yml` relocation that silently changed the Compose project name. Applies on any machine, not just where these specific incidents happened. See [lessons-learned.md](docs/lessons-learned.md) for the full incidents and more.
- **Centralize a config value in one place instead of repeating the literal across files.** E.g. don't let the same Docker image version drift by being hardcoded independently in `Dockerfile`'s `ARG` and in prose docs — the concern is drift risk, not tidiness. Historical/dated facts ("verified against version X on date Y") are exempt; this is about *live* config values.
- **Don't manually wrap prose lines when writing documents.** The editor in use (IntelliJ) has soft-wrap on; write each paragraph as one long source line. Applies to markdown/prose — code comments still wrap per normal language convention. Don't proactively reflow an old file for this; only fix it while otherwise editing that file.
- **All development and testing happens inside the `docker/` sandbox, never directly against the host's own node/opencode/npm install.** Run `./tests/run-all.sh` to build the sandbox image and run the whole suite; iterate faster with `docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh`. Always go through `docker/dev.sh`, not `docker compose` directly — it isolates this worktree's Compose project so concurrent worktrees never collide (see `docker/docker-notes.md`). Exception: `tests/integration/docker-prompt-override.test.sh` runs on the host because it's what invokes `docker run` in the first place — but everything it actually asserts on still executes inside a disposable container.
- **Once a branch's PR merges, start the next piece of work from a fresh branch cut off the updated `master`, not by continuing to commit on the already-merged branch.** Its PR is closed; new commits pushed there just create confusion about which PR they belong to, and `master` already has everything from it (a real merge commit, not squash/rebase, so the old branch is a plain ancestor — nothing is lost by abandoning it). In a Claude Code session tied to a worktree/branch for this reason, the clean way to pick up unrelated new work is usually a fresh session (its own worktree + branch from current `master`) rather than repurposing the current one; for a small change within the same session, `git fetch && git checkout -b <new-branch> origin/master` works fine too (see the commit that added this line for a worked example).
- **When a branch falls behind `master` (e.g. a PR reports a conflict), catch it up with `git fetch && git rebase origin/master` on the branch, then `git push --force` to that same branch — don't `git merge origin/master` into it.** Landing a finished PR into `master` is the opposite: always a real merge commit (`gh pr merge --merge`), never squash or rebase-merge (see the bullet above). Force-pushing is fine, routine even, on a feature/topic branch nobody else depends on; the standing caution against rewriting history only applies to `master`/other shared branches, not here.
- **Don't hedge a claim about a generic host/platform capability with "validated on model X" when nothing about it is actually model-specific.** E.g. opencode's `agent.*.prompt` config field (what the Qwen prompt override uses) is a generic host mechanism with no Qwen-specific code path, so framing it as needing "validation against the Qwen deployment" before it could be called generic was an unwarranted hedge. Reserve "tested/validated against X" qualifiers for things that genuinely differ per model or provider (tool-call parsing quirks, context-window limits, thinking-token handling, etc.).
- **Never persist notes about this project in an AI tool's own per-machine/per-account store (e.g. Claude Code's `~/.claude/projects/**` memory)** — it isn't visible from another machine, account, or fresh clone, defeating the entire point of a single-person project that moves across environments. Anything worth remembering (preferences, corrections, lessons, project context) goes in this file or `memory/`, both git-tracked; see `memory/MEMORY.md`'s intro for the same rule from the other side.
- **Write reader-facing docs (README, SETUP, this file, `docs/feature-points/*`, subpackage READMEs) to answer "what's true now and what should I do next," not as a changelog of how it got there.** Avoid dates unless the date changes what the reader should do, and avoid "previously"/"renamed from"/"converted from"/"this session" phrasing or release-story detours inside otherwise-current instructions — that reads as a session log, not documentation, and makes a future reader reconstruct the current rule from a timeline instead of just reading it. Don't explain the same decision in more than one place either; link instead. Dated history still belongs in files whose whole purpose is historical/decision-oriented — `docs/lessons-learned.md`, `mcp-servers/TODO.md`, narrowly-scoped decision notes — link to those rather than duplicating the story inline. For a manually-triggered pass auditing docs against this rule, see [docs/doc-clarity-review.md](docs/doc-clarity-review.md) — it also covers the trap of deleting real design rationale along with the dated chronology it's wrapped in.

- **Two separate machines, don't conflate them.** (1) The restricted/offline machine: single-user, Windows, git-bash, no public internet — where SETUP.md actually gets executed (also used via `web`/`serve` modes, not just CLI — all interfaces read the same `opencode.json`). opencode itself is already installed there via `npm install -g opencode-ai`. **Confirmed 2026-09-17 (Franco, high confidence): this machine does have a working internal npm registry reachable over the intranet, for downloading only — it cannot be used to publish/release this repo's own code.** "No internet" only ever meant no public/external access, not no registry at all. This is why `mcp-servers/oracle/`/`mcp-servers/loki/`'s third-party npm dependencies (`@modelcontextprotocol/sdk`, `oracledb`) install directly via `npm install` now (SETUP.md steps 6/7, see `mcp-servers/TODO.md`) — that registry is a full mirror of public npm, not a curated subset — and the same mirror also resolves `plugins/`'s own packages by bare name, since those are published to the public registry too (see the table entry below). (2) A *separate* vLLM model-serving machine reachable over the restricted machine's internal network — Franco has no admin access to it, only consumes it as an API client; no multi-user file-contention concern on the opencode side.
  Model in use: **`Qwen3.6-35B-A3B`** (real, released 2026-04-16, Apache 2.0, sparse MoE — postdates the knowledge cutoff, don't rely on training-data recall). Native context 262,144 tokens, extensible to 1,010,000 via RoPE scaling — but **the actual deployed context is confirmed by Franco at only 128K** (2026-09-18, chat, high confidence — not yet traced to a specific vLLM flag like `--max-model-len`), so don't assume the full native/extensible figure is actually usable in practice; treat 128K as the real ceiling for anything context-budget-sensitive until the gap is explained. Has a "thinking preservation" feature (retains reasoning traces across multi-turn) — worth checking whether `opencode.json`'s model config sets `reasoning`/`interleaved` to use it. Hardware specs of the model server unknown. `$CONFIG_DIR` on the restricted machine is opencode's default (no override).
- **Known model quirk, not an opencode/repo issue**: a "tool call not supported" error was hit on one smaller Qwen model (referred to as "qwen2.7b", exact model unconfirmed). Not fixable from this repo's prompt override; if it recurs, check vLLM's `--tool-call-parser` flag on the model server.
- **The models.dev catalog fetch doesn't block startup on a fully offline machine** — a build-time snapshot is embedded in the offline binary. Only cosmetic fallout is an hourly failed-fetch log line; silence with `OPENCODE_DISABLE_MODELS_FETCH=1`, and add `OPENCODE_MODELS_PATH=<path>` (pointing at `deploy/models-dev-snapshot.json`, see SETUP.md step 3) for fresher data — both vars are needed together. Doesn't matter much either way: this setup's Qwen provider is defined by hand in `opencode.json`, not looked up from the catalog at all.
- Claude's own cross-session memory about this project lives at `~/.claude/projects/<encoded-cwd>/memory/` — the encoded-path segment is machine/account-specific, so don't assume a path recorded here still resolves on whatever machine you're reading this from; check `MEMORY.md` in that directory.
- **Whole-repo npm publish, and every package in this repo shares one version number.** The root `package.json` packages the entire git-tracked tree as `@kealthas-dev/opencode-toolkit` on public npmjs.com — not a real dependency for anything, purely a second download channel alongside the `v*`-tag GitHub Release zip (`.github/workflows/release.yml`). The restricted machine's internal npm mirror can then fetch it with `npm pack @kealthas-dev/opencode-toolkit@<version>`. `license: "UNLICENSED"` because public/downloadable here is a transfer mechanism, not an invitation for outside use. `scripts/publish-npm.sh` exports the current `HEAD` with `git archive` into a clean temp dir before publishing, which avoids sweeping local untracked files into the tarball. Keep the intentionally-empty root `.npmignore`: its presence prevents npm from falling back to `.gitignore` and dropping gitignored-but-tracked payloads such as `docs/opencode-docs-reference/` and `deploy/models-dev-snapshot.json`. **Pushing a `v*` tag is the single release trigger for every npm package in this repo** (root, `plugins/*` x3, `mcp-servers/oracle`, `mcp-servers/loki`, `mcp-servers/java-lsp`, `mcp-servers/spring-lsp` — 7 packages total) — `release.yml` loops over all of them, sets each one's version from the tag (`npm pkg set version=...`, skipping any already published at that exact version so a workflow re-run is safe), and publishes via npm Trusted Publishing (OIDC, `id-token: write`, no stored token). None of the individual `package.json` `version` fields are meaningful on their own — Franco decided against independent per-package versioning (bumping only the packages that actually changed) specifically to avoid tracking N different version numbers across N files; a release bumps every package together, even ones with no code change, which is the accepted tradeoff. The workflow must publish before building the GitHub Release zip, so the zip artifact cannot be swept into the npm tarball. A brand-new package's *first-ever* publish can't go through this workflow — npm Trusted Publishing is configured on an existing package's Settings page on npmjs.com, so the package has to exist first via a real account login (`npm login` + `npm publish` by hand) before that binding can even be created; every package above has already been through that bootstrap once.
