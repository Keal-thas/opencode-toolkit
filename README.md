# opencode tooling workspace

A workspace for building on top of `opencode` (the CLI coding agent): a system-prompt override, custom opencode plugins, MCP servers for LAN-internal ops tooling and Java/Spring code intelligence, and a script that uses opencode to analyze a large codebase.

The target machine is Windows + git-bash with no internet. The repo is downloaded as a zip (or `npm pack @kealthas-dev/opencode-toolkit`) on a connected machine and carried over; everything below works offline from the extracted copy.

- [SETUP.md](SETUP.md) — the deployment steps, written to be handed to an agent and executed one by one. [SETUP.zh.md](SETUP.zh.md) is the same steps at a glance, in Chinese.
- This README — what each part is and why it looks the way it does.
- [CLAUDE.md](CLAUDE.md) — how to work on the repo. [TODO.md](TODO.md) — what is next.

## System-prompt override

opencode replaces the system prompt it sends to a model through its own config; no plugin is needed for the override itself.

### What's in `deploy/`

- `system-prompt.txt` — the replacement prompt. Also carries a `# Memory` policy section for the memory MCP server.
- `opencode.json.example` — wires `system-prompt.txt` in, enables the plugins and MCP servers listed in the two index READMEs above, and defines the `review-gate` agent used by `llm-review-gate`. Each MCP server still needs its own process started or its credentials supplied per SETUP.md before it works; disable in `opencode.json` whichever ones are not wanted.
- `models-dev-snapshot.json` — a local copy of opencode's models.dev catalog; point `OPENCODE_MODELS_PATH` at it so the offline machine never tries to fetch it live (SETUP.md step 3). Optional, since the offline build has its own baked-in snapshot. Generated; refresh with `./deploy/fetch-models-snapshot.sh`. See [docs/generated-files.md](docs/generated-files.md) for why it is both tracked and gitignored.

### How the override works

opencode's per-agent `prompt` field fully replaces the built-in provider prompt (e.g. `default.txt`), verified against a real install. The `<env>` block (working directory, git check, platform, date) and any configured `instructions` files are still generated by opencode and appended after the custom prompt.

`build`, `plan` and `general` get this prompt (see `deploy/opencode.json.example`). `compaction`, `summary`, `title` and `explore` each ship a narrow native prompt unrelated to coding style, and overriding those would hurt them. `general` needs the override explicitly: upstream sets no `prompt` for it (same as `build`/`plan`), so left alone it would fall back to the full `default.txt`.

### Why system-prompt.txt looks the way it does

It is written for a professional user, so the hand-holding tone and few-shot examples of upstream's `default.txt` are stripped. Four things from upstream are kept on purpose:

- Never invent or guess a URL.
- Explain a non-trivial or state-changing command before running it.
- Don't take actions beyond what was asked.
- Delegate broad, open-ended exploration to the Task tool. Upstream says this "to reduce context usage"; a plain "prefer grep/glob" gives the model no prompt-level reason to ever spawn a subagent.

The first three are safety and quality guardrails, not hand-holding.
