# mcp-servers/ backlog

**All of these should be built as `type: "remote"` MCP servers (a persistent HTTP process opencode connects to) from the start, not `type: "local"` (opencode-spawned over stdio)** — `oracle/` was originally built local/stdio and converted to remote/HTTP later (2026-09-14, see `mcp-servers/oracle/README.md`'s Design and Status sections for why and how); the later servers below shouldn't repeat that detour. Reuse `oracle/src/server.ts`'s pattern: Node's built-in `http` plus `@modelcontextprotocol/sdk`'s `StreamableHTTPServerTransport` in stateless mode (`sessionIdGenerator: undefined`, a fresh `Server`/transport pair per request), no extra HTTP framework dependency needed.

Tested end-to-end against a real Loki instance in the docker sandbox (`docker/docker-compose.loki.yml`) — see `mcp-servers/loki/README.md`'s Status section and `docs/feature-points/14-loki-mcp-server.md`.
- [x] **java-lsp / spring-lsp** — done 2026-09-18, jdtls vendored + both published to npm 2026-09-21 (see the publish item below). Not internal-ops LAN tooling like the four above (Oracle/Loki/Redis/MySQL) — these two spawn and drive a real LSP server (jdtls, and VMware's `spring-boot-language-server`) over stdio instead of hitting an HTTP API, but still `type: "remote"` MCP servers per this file's own rule, for the same reason: LSP is a genuinely stateful session (project indexing, incremental document sync), so `server.ts` keeps one LSP-client singleton alive for the server's whole lifetime rather than per-request, while the outer MCP/HTTP layer stays stateless-per-request like `oracle`/`loki`. Built because opencode's own built-in `jdtls` LSP integration only auto-detects `java` on `PATH` with no way to point it at a different JDK for the server process itself (see both packages' READMEs' "JDK version" sections). `lsp-client.ts` (the shared framing/handshake/document-sync engine) is duplicated verbatim between the two packages rather than pulled in as a shared dependency — see `mcp-servers/java-lsp/README.md`'s Design section for why. Both verified end-to-end against real, real language-server processes (jdtls 1.61.0, vendored — see the publish item below; the vendored `spring-boot-language-server` 2.5.0-SNAPSHOT, extracted from VMware's VS Code extension since it isn't published to any package registry — see `mcp-servers/spring-lsp/README.md`'s Vendoring section, including its real ~81MB size, by far the largest binary this repo has committed). `java-lsp` is fully verified with rich results (real symbol resolution, hover, references, definitions) against a plain Java file. `spring-lsp` is only verified at the protocol/plumbing level — its Spring-specific richness (bean graph, config-property completion) needs either a real Maven/Gradle project with resolved dependencies, or pairing with a companion jdtls via the "classpath listener" mechanism VS Code's Java+Spring extensions use together — neither was set up here, see `mcp-servers/spring-lsp/README.md`'s Status section for the exact failure mode (empty results, not errors) and what's needed to fix it. Wired into `deploy/opencode.json.example` (`enabled: true`, ports 8092/8093) and now SETUP.md steps 8/9 too.

  - **Follow-up done 2026-09-24:** the `<X>_CONFIG_FILE` env var (arbitrary path) replaced with `<X>_CONFIG_ENV` (a plain name, validated against `[a-zA-Z0-9_-]+`) across all four servers. Real bug on the Windows target machine: a shell that didn't expand `~` (or a quoted value that suppressed bash's own expansion) handed the process a literal `~`, which `path.resolve()` then resolved against whatever `cwd` happened to be, producing a bogus path instead of erroring. The fix stops taking a path from user input at all — the location is always `homedir()` + a fixed subpath, either `config.json` (no env var set) or `configs/<name>.json` (`<X>_CONFIG_ENV=<name>`). See `mcp-servers/oracle/README.md`'s Configuration section for the updated fullest writeup.

- [ ] `oracle/`'s `executeQuery()` has no result-size cap and issues no session-level statements before running the agent's SQL. Worth adding together: (1) a `maxRows`-based cap on `connection.execute()` (fetch `N+1`, trim to `N`, return a `truncated: true` flag when exceeded — driver-level, so it applies regardless of the SQL's shape, unlike trying to inject `FETCH FIRST`/`LIMIT` into arbitrary agent-written SQL text — cap configurable via a field in the database config file, see `mcp-servers/oracle/README.md`'s Configuration section for the file-based config this would extend), since right now a broad `SELECT` against a large table fetches and JSON-serializes every row into the tool response with no limit; (2) `SET TRANSACTION READ ONLY` issued right after `getConnection()`, before the agent's SQL runs — verified live against the sandbox's `oracle` instance (2026-09-21) to reject DML (`ORA-01456`) even for an account that genuinely holds INSERT/UPDATE/DELETE grants, so this is a real independent layer on top of whatever `ORACLE_USER` happens to have, not just a restatement of the account's own grants; (3) `ALTER SESSION SET CURRENT_SCHEMA` support, confirmed wanted at two config levels (2026-09-21, Franco, high confidence): a project/deployment-level default (an `ORACLE_DEFAULT_SCHEMA` field in the database config file, applied on every connection if set) plus a user/call-level override (an optional `schema` argument on the `oracle_query` tool itself, so one deployment isn't locked to a single schema if a particular query needs a different one) — so agents don't have to qualify every table name with `schema.table`; (4) `ALTER SESSION SET NLS_DATE_FORMAT` for consistent date rendering — an ergonomics nicety, not a safety measure. Doesn't replace using a read-only DB account (see `mcp-servers/oracle/README.md`'s Recommended read-only account section) — that stays the primary boundary; this is defense-in-depth plus making the tool more agent-friendly out of the box.
