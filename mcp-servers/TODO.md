# mcp-servers/ backlog

**All of these should be built as `type: "remote"` MCP servers (a persistent HTTP process opencode connects to) from the start, not `type: "local"` (opencode-spawned over stdio)** — `oracle/` was originally built local/stdio and converted to remote/HTTP later (2026-09-14, see `mcp-servers/oracle/README.md`'s Design and Status sections for why and how); the later servers below shouldn't repeat that detour. Reuse `oracle/server.js`'s pattern: Node's built-in `http` plus `@modelcontextprotocol/sdk`'s `StreamableHTTPServerTransport` in stateless mode (`sessionIdGenerator: undefined`, a fresh `Server`/transport pair per request), no extra HTTP framework dependency needed.

- [x] **Loki** — done 2026-09-14. `mcp-servers/loki/` exposes `loki_query_range`/`loki_labels`/`loki_label_values` against the Loki HTTP query API (just `fetch`, no driver dependency, as planned), `type: "remote"` from the start. Tested end-to-end against a real Loki instance in the docker sandbox (`docker/docker-compose.loki.yml`) — see `mcp-servers/loki/README.md`'s Status section and `docs/feature-points/14-loki-mcp-server.md`.
- [x] **java-lsp / spring-lsp** — done 2026-09-18. Not internal-ops LAN tooling like the four above (Oracle/Loki/Redis/MySQL) — these two spawn and drive a real LSP server (jdtls, and VMware's `spring-boot-language-server`) over stdio instead of hitting an HTTP API, but still `type: "remote"` MCP servers per this file's own rule, for the same reason: LSP is a genuinely stateful session (project indexing, incremental document sync), so `server.js` keeps one LSP-client singleton alive for the server's whole lifetime rather than per-request, while the outer MCP/HTTP layer stays stateless-per-request like `oracle`/`loki`. Built because opencode's own built-in `jdtls` LSP integration only auto-detects `java` on `PATH` with no way to point it at a different JDK for the server process itself (see the session notes this was built from, and both packages' READMEs' "JDK version" sections). `lsp-client.js` (the shared framing/handshake/document-sync engine) is duplicated verbatim between the two packages rather than pulled in as a shared dependency — see `mcp-servers/java-lsp/README.md`'s Design section for why. Both verified end-to-end against real, real language-server processes (jdtls 1.61.0 via `brew install jdtls`; the vendored `spring-boot-language-server` 2.5.0-SNAPSHOT, extracted from VMware's VS Code extension since it isn't published to any package registry — see `mcp-servers/spring-lsp/README.md`'s Vendoring section, including its real ~81MB size, by far the largest binary this repo has committed). `java-lsp` is fully verified with rich results (real symbol resolution, hover, references, definitions) against a plain Java file. `spring-lsp` is only verified at the protocol/plumbing level — its Spring-specific richness (bean graph, config-property completion) needs either a real Maven/Gradle project with resolved dependencies, or pairing with a companion jdtls via the "classpath listener" mechanism VS Code's Java+Spring extensions use together — neither was set up here, see `mcp-servers/spring-lsp/README.md`'s Status section for the exact failure mode (empty results, not errors) and what's needed to fix it. Wired into `deploy/opencode.json.example` (`enabled: true`, ports 8092/8093).
