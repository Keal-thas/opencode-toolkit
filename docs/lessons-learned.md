# Lessons learned

Historical debugging/verification incidents from building this repo, compressed to conclusion + trigger context. Read before repeating investigative work already done here. Linked from [CLAUDE.md](../CLAUDE.md)'s Preferences section — that file has the current, actionable rules; this one has the "why"/precedent behind them and one-off findings that don't generalize into a rule.

- **Don't undersell this repo's scope as just the Qwen prompt override.** It's Franco's general opencode tooling workspace (prompt override, plugins, scripts, MCP servers) — the override is just the first piece and the repo's namesake, not the whole scope. Corrected 2026-09-13 after an audit ranked `module-analysis/`/`plugins/` as unrelated hitchhikers.

- **No single authoritative list of `OPENCODE_*` env vars exists, not even in official docs.** `cli.mdx`'s tables and the actual source (`packages/core/src/flag/flag.ts`) disagree both ways — `OPENCODE_MODELS_PATH` (which SETUP.md depends on) is real but undocumented; some documented vars aren't in that one source file (read from elsewhere in the codebase). When a specific var matters, grep the real source rather than trusting either list.

- **Verify-against-real-system incidents** (supporting the Preferences rule): a third-party gist's fallback-prompt claim was false, settled by testing; whether `agent.prompt` replaces vs. appends to the provider prompt was settled via `opencode debug config` + a throwaway plugin; `opencode debug agent <name>` gives every built-in agent's resolved prompt directly and confirmed `explore`/`general` silently fall back to `build` under `opencode run --agent` — the same mechanism that caused the real `module-analysis` safety bug.

- **Prefer the simplest mechanism, even if it means discarding earlier work.** First approach hand-rolled a JS plugin intercepting `experimental.chat.system.transform` to rewrite the prompt, including the `<env>` block by hand. `agent.prompt` + `{file:...}` in plain `opencode.json` does the same natively (opencode builds the env block itself) — discarded the plugin version once this was proven.

- **When cutting "hand-holding" content from a prompt, diff against the original first.** Some apparent hand-holding (URL-guessing warning, explaining state-changing commands, not overstepping scope) was actually a safety guardrail. A line-by-line diff against upstream `default.txt` caught this; a first pass by feel missed it.

- **A subagent reporting "waiting" or similar isn't a real result.** Resume it and demand an actual answer plus confirmation that any cleanup it owed actually happened.

- **opencode enforces behavior via permissions, not prompt text.** `plan`'s "can't edit files" comes entirely from its permission ruleset (`edit: deny`), not prompt wording — `session/system.ts`'s base-prompt selection branches only on model ID, never agent/mode. Confirmed by testing: sharing one prompt across `build`/`plan`/`general` didn't affect `plan`'s edit restriction. Don't assume the reverse elsewhere, though — anything not permission-enforced (tone, delegation instructions) only exists because the prompt says so.

- **The CLI's "can't run a subagent directly" restriction is CLI-argument parsing, not server-side — but that doesn't make direct SDK agent invocation a safe substitute for a real permission-layer guarantee.** Found 2026-09-14 rewriting `module-analysis` to use `@opencode-ai/sdk`: `client.session.prompt({body:{agent:"explore",...}})` genuinely runs as `explore` at the SDK/HTTP layer (no `build` fallback). But `explore`/`general`'s permission arrays are just blanket `allow` — their "read-only" framing is enforced purely by their own prompt text, not a permission rule, unlike `plan`'s real `edit: deny`. For unattended use over untrusted code, `plan` stays the safer choice specifically because of that permission-layer denial.

- **The Task tool's subagent result is fragile.** `tool/task.ts` returns only the subagent's last text block (`parts.findLast(p => p.type === "text")`) — no concatenation of earlier text/tool output, silent `""` if the final message has no text part (e.g. it ends on a tool call). No error either way. A real risk for a smaller model that doesn't reliably self-summarize.

- **ripgrep keeps honoring `.gitignore` for a path even after it's already git-tracked — this is what makes it safe to gitignore `docs/opencode-docs-reference/` without untracking it.** Verified live: `git check-ignore`/`git status` treat the already-tracked directory as unaffected, but `rg` still skips it in broad searches (git and ripgrep disagree on what "ignored" means for tracked paths). One real cost: a brand-new file added under a gitignored-but-tracked path needs `git add -f`, since it won't show up as untracked on its own.

- **Checking for full-width/Chinese punctuation via shell `grep -P` is unreliable** — multi-byte Unicode literals in the pattern get silently garbled (matches ASCII quotes instead of the intended curly/full-width chars). Use a small Python script with explicit `chr(0xFF0C)`-style codepoints instead. Relevant given the global English-punctuation-only rule applies even to Chinese text; missed once writing `SETUP-walkthrough.zh.md`, caught on a follow-up review.

- **`plugins/` TypeScript rewrite (2026-09-13): verify a new SDK dependency against the real installed types, not just its docs page.** `tsc --noEmit` against the real `@opencode-ai/plugin` tarball caught nothing wrong (hook names hadn't drifted from the real `Hooks` interface) — but running the full sandbox afterward surfaced two real, unrelated issues: Node 20 has no native TS support (fixed by bumping the base image to Node 22), and `node --test tests/unit` behaves differently across Node 20→22 on a bare directory, no glob (fixed with an explicit glob in `run-in-container.sh`). Moral: a Node bump for one reason can silently break unrelated things — always run the full suite after, not just the original fix.

- **`deploy/system-prompt-tools.ts` rewrite (2026-09-14): couldn't fully verify opencode's plugin loader actually loads a local `.ts` file at runtime.** Types checked out clean against real cached SDK types. At the time, `opencode debug config` appeared to accept a `.ts` plugin path without ever actually importing it (pointing it at deliberately broken syntax raised no error). Proceeded anyway since `plugins.mdx` documents local `.ts` plugins as first-class and this plugin is diagnostic-only. **Update, 2026-09-14 (docker sandbox concurrency redesign):** this was incomplete — `opencode debug config` does trigger a real dependency-installation step for a configured plugin (confirmed installing the plugin's ~26-package `node_modules` tree into `~/.config/opencode`, ~50-60s wall time, exit 0 — see the Dockerfile pre-warm step below and `docker/docker-notes.md`'s "Plugin dependency pre-warming"). Left unresolved: whether it also fully *executes* the plugin's exported hook functions, vs. only resolving/installing its import graph — a syntax error deep inside a hook body might still not surface this way. Worth a real spot-check via an actual chat request (blocked by the `opencode run` hang bug below) before fully trusting `debug config` as a stand-in for a live run.

- **`opencode run` hangs indefinitely right after the `init` bootstrap log line — a real, unresolved, unrelated bug in the docker sandbox.** Reproduced with zero plugins configured, a working API key, and a reachable API host — so not plugin-related, not a stale-lock issue. Root cause not chased since it's orthogonal to the Qwen override (verified via `opencode debug config`, not `opencode run`) and `./tests/run-all.sh` doesn't exercise `opencode run` at all. Needs its own investigation session before relying on `opencode run` in this sandbox.

- **`StdioClientTransport` (from `@modelcontextprotocol/sdk`) doesn't inherit the parent process's environment by default.** A client that spawns an MCP server directly via that transport needs an explicit `env: process.env` passed in, or the spawned server sees none of its env vars and exits immediately. Found 2026-09-13 verifying `mcp-servers/oracle/server.js` — doesn't bite a shell-spawned child or `node:child_process.spawn` (both inherit by default), only that one SDK class. Moot for `mcp-servers/oracle/` itself since 2026-09-14 (it's now `remote`/Streamable HTTP, nothing spawns it via `StdioClientTransport`), but worth remembering if a future `local`/stdio MCP server in this repo hits the same thing.

- **Docker sandbox concurrency redesign (2026-09-14, implementing TODO.md's decided direction): the `COMPOSE_PROJECT_NAME` env var overrides a compose file's own top-level `name:`, including for a file that never asked for that override.** `docker/dev.sh` exports `COMPOSE_PROJECT_NAME` (hashed from the calling worktree's path) for `docker-compose.yml`, but originally did so *before* also invoking `docker-compose.oracle.yml` (meant to stay on its own fixed project name) in the same shell — the exported var leaked into that second invocation too, silently renaming the "shared" oracle project per-worktree and defeating the whole point of splitting it out. Caught immediately by testing live (a real container-name conflict against a pre-existing oracle container), not by reading the script. Fixed by reordering: bring oracle up first, only export `COMPOSE_PROJECT_NAME` afterward. Verified the fix with real concurrent runs: 5 parallel `docker/dev.sh run --rm opencode-dev` in one worktree, and two different worktree paths running concurrently, all with distinct auto-derived container names and zero collisions.

- **Don't "fix" punctuation in verbatim captured data.** `deploy/captured-example-prompt.txt` has real full-width Chinese punctuation left as-is on purpose — it's a literal capture, not prose authored for this repo. The punctuation rule applies to docs authored here, not raw logged evidence.

- **A `History:` paragraph can carry real design rationale, not just chronology — deleting the whole thing during a doc-clarity pass can silently delete the rationale too.** Trimming `docker/docker-notes.md`'s `plugins/` packaging note (2026-09-19 doc-clarity pass) removed a `History:` paragraph that explained why per-plugin npm-tarball packaging was chosen over opencode's simpler, documented local-plugin-directory mechanism — the alternative gives every local plugin one shared dependency tree via a single `$CONFIG_DIR/package.json`, with no per-plugin version isolation. That reasoning wasn't preserved anywhere else in the repo after the cut. See [docs/doc-clarity-review.md](doc-clarity-review.md) for the checklist step this motivated (separate chronology from rationale before deleting either).

- **A git workflow note once got saved to Claude Code's own per-machine `~/.claude/projects/**` memory instead of this repo's git-tracked memory — invisible from any other machine or account, defeating the entire point of keeping project memory git-tracked.** Migrated back into `CLAUDE.md`/`memory/MEMORY.md` and the stray external file deleted (2026-09-19). `memory/MEMORY.md`'s own "never do this" rule used to carry this incident as an inline parenthetical; moved here during a doc-clarity pass since the rule's rationale already stands on its own without the incident story.

- **A doc-clarity pass that only greps for known trigger words (`previously`, `History:`, etc.) misses drift that says the same thing differently.** A first grep-only re-review (2026-09-19) came back nearly clean; actually reading files it hadn't touched turned up two real misses the trigger-word list couldn't catch: `SETUP.md`/`SETUP-notes.zh.md` step 4 justified installing the diagnostic plugin with "this is the first time this setup runs against the real Qwen model" — a snapshot-in-time claim with no date attached, silently false the next time the same steps run, and invisible to the checklist's original pattern list because it's phrased as a fact about *now*, not as history; and `docs/feature-points/11-release-automation.md` still described the release workflow as a GitHub-zip-only mechanism, missing the npm-publish step `.github/workflows/release.yml` had already gained — caught only by reading the real workflow file, not by comparing docs against each other. Both fixed the same day. See [docs/doc-clarity-review.md](doc-clarity-review.md), which gained checks for both failure modes from this.
