# opencode memory (via the official `server-memory` MCP server)

opencode has no cross-session memory of its own — `AGENTS.md`/`instructions` are static and fully re-injected every session, and skills are pre-written instructions, not runtime-accumulated knowledge (see `docs/opencode-docs-reference/rules.mdx`/`skills.mdx`). This wires in Anthropic's official `@modelcontextprotocol/server-memory` package instead of writing a server of our own: a local knowledge graph (entities/relations/observations) persisted as a JSONL file, searched by keyword match, not embeddings.

**Why this over a vector/RAG approach:** this only covers the "small, structured, behavioral/decision memory" use case (user preferences, project facts, past decisions) — not "search a large corpus of reference documents by meaning," which is a different problem needing an embedding model and a vector store, both unverified as feasible on the actual offline target machine. Keyword-only memory is the right scope for the former: zero embedding dependency, Node/npm (matches this workspace's existing MCP tooling, unlike a Python/`uv`-based alternative), and it's the officially-maintained default the wider ecosystem converges on for this exact use case. The document-corpus/RAG problem is intentionally not addressed here — see `TODO.md`.

**Not hosted in `mcp-servers/`** — that directory is hand-rolled servers this repo wrote against the raw SDK for LAN-internal ops tooling (Oracle, Loki). This is neither: it's an unmodified upstream package, wired in purely through config (`deploy/opencode.json.example`'s `mcp.memory` entry + `SETUP.md` step 10) and a system-prompt policy (`deploy/system-prompt.txt`'s `# Memory` section, telling the model when to read/write it — without this, the tools exist but nothing prompts the model to use them reliably).

Wired as `type: "local"` — opencode spawns `mcp-server-memory` itself (installed globally via `npm install -g` against the internal registry, same as steps 6/7's third-party deps), unlike Oracle/Loki's `type: "remote"`, which needs a separately-supervised process.

**Known limitations, not fixed here:**
- No automatic retrieval at session start — the model has to decide to call `search_nodes`/`read_graph` based on the system-prompt instruction. A stronger version (a plugin's `session.created` hook force-injecting the graph, closer to how Claude Code's own memory index is unconditionally loaded every conversation) is a possible future enhancement, deferred until it's clear the prompt-only version isn't reliable enough in practice.
- Write quality has no review/consolidation pass — entries accumulate however the model judges in the moment, same failure mode as any note-taking system. An opencode skill mirroring Claude Code's `consolidate-memory` would need to be built separately if this becomes a problem.
- `$CONFIG_DIR/memory.jsonl` is local machine state, not backed up or version-controlled by anything in this repo (unlike this repo's own git-tracked `memory/`) — an intentional choice for now (SETUP.md step 10 flags it explicitly), not a settled decision.

**Tested:** `tests/integration/mcp-memory/memory.test.mjs` — spawns the real installed package over stdio (matching how opencode itself starts a `type: "local"` server) and drives it with a real `@modelcontextprotocol/sdk` client: tool listing, a `create_entities`/`search_nodes` round-trip, and confirming `MEMORY_FILE_PATH` actually gets written to disk. This verifies the upstream package behaves as documented; it does not verify anything about the real target machine (global npm install actually landing `mcp-server-memory` on `PATH` there, or the real Qwen model reliably calling these tools per the prompt instruction) — both flagged as open in `SETUP.md`'s "Report back" section.
