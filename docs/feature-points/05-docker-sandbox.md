# Docker dev/test sandbox

Lives in `docker/`. An isolated container (real `opencode` install, pinned version via `docker/.env`, non-root `dev` user) for exercising the prompt/plugins against a real opencode without touching the host's own config. Launched only via `docker/dev.sh`, which hashes the calling worktree's path into `COMPOSE_PROJECT_NAME` so concurrent worktrees never collide on container/network names. No config/data volumes anymore — `docker-entrypoint.sh` regenerates `opencode.jsonc` fresh on every start, and opencode installs the plugin's `node_modules` fresh from the npm registry each time too. The repo is live bind-mounted; provider API keys load from a read-only `~/.keys` mount, never written to any tracked file. `oracle`/`loki` (for `mcp-servers/oracle/`/`mcp-servers/loki/`) each live in their own always-shared compose project (`docker-compose.oracle.yml`/`docker-compose.loki.yml`), joined over an external network.

**Tested:** this *is* the execution environment for the rest of the suite (`tests/run-in-container.sh` runs inside it via `docker/dev.sh run`) — plus `tests/integration/docker-prompt-override.test.sh` specifically automates the sandbox's "does the override actually work" check. Per-worktree isolation verified live with concurrent same-worktree and cross-worktree runs — see `docs/lessons-learned.md`.
