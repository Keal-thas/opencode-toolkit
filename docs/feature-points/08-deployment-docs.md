# Deployment docs

`SETUP.md` is written to be executed *by an agent* on the target machine (no public internet but a working internal npm registry mirror, git-bash on Windows) — copies files in, merges the `agent` config key, installs the viewer plugin (step 4) and the hook-logger/llm-review-gate plugins (step 5, general-purpose tooling unrelated to the prompt override), wires in the Oracle, Loki, and Memory MCP servers (steps 6–8, see feature points 13/14/15), verifies, reports back. All of these ship enabled by default in `deploy/opencode.json.example`; whoever runs SETUP.md decides which to actually keep configured (each plugin is independently removable from the `plugin` array, each MCP server independently toggled via its `enabled` field). Both plugin steps just reference the plugin by bare scoped package name in the `plugin` array — no version, no path, no `file:` spec — opencode's own npm-plugin loader installs each from the real public npm registry itself on first use — see `docs/feature-points/02-system-prompt-tools-plugin.md`. `USAGE.zh.md` is a short Chinese walkthrough of the same steps, not meant to be executed literally.

**Tested:** indirectly — `tests/unit/config-consistency.test.mjs`'s SETUP.md/example-config drift check is the one piece of SETUP.md's *content* under test. The step-by-step procedure itself can only really be validated by actually running it on the target machine, which is out of reach from here.
