# Release automation

`.github/workflows/release.yml`: on a `v*` tag push, publishes the repo to npm via Trusted Publishing, then builds a zip of the repo (including `.git`) and publishes it as a GitHub release — the zip is the mechanism that gets the repo onto the offline target machine (per SETUP.md's "downloaded as a zip" assumption); npm is the second channel the internal npm mirror can pull from instead. The npm publish step must run before the zip build, so the zip's own working-tree artifact can't get swept into the npm tarball. See [docs/npm-publishing.md](../npm-publishing.md) for the full mechanism and current package-name status.

`.github/workflows/publish-plugins.yml`: a separate, independent workflow for `plugins/hook-logger/`, `plugins/llm-review-gate/`, `plugins/system-prompt-tools/` (npm names `@kealthas-dev/opencode-hook-logger` etc.) — each its own npm package with its own version, unrelated to the repo's `v*` release tags. Triggers on a plain push to `master` touching any `plugins/*/package.json`; for each of the three, checks whether that package's current `package.json` version is already on the npm registry and publishes it if not (an "already published?" registry check, not a git diff — safe to run on any matching push without risking a duplicate-publish failure). Same Trusted Publishing/OIDC mechanism as `release.yml`, with its own Trusted Publisher entry configured per package on npm's Settings pages. Publishing a new version is tag-free and human-free: bump a plugin's `package.json` version, merge to `master`, done.

**Untested end-to-end** (no real version bump has gone through `publish-plugins.yml` yet) — would require merging a real version bump to `master`, a real, visible action, not something to trigger from an automated test run. The underlying npm-install mechanism it produces (a plugin resolvable by opencode's own npm-plugin loader) is independently confirmed working — see `docker/docker-notes.md`.
