# gitbash-edit-path-fix.ts plugin

Lives in `plugins/`. Works around a real bug in the target machine's opencode install (Windows + Git Bash, see [docs/deployment-environment.md](../deployment-environment.md)): the built-in `edit` tool (`packages/opencode/src/tool/edit.ts` in [anomalyco/opencode](https://github.com/anomalyco/opencode)) never re-resolves a Git-Bash/MSYS/Cygwin/WSL-style absolute path like `/c/Users/franco/file.ts`, because Node's `path.win32.isAbsolute()` already calls that "absolute" (root-relative, no drive letter) — so it skips the branch that would otherwise resolve it and hands the literal string straight to `fs.stat`/`fs.readFile`/`fs.writeFile`, which Windows then resolves against whatever the *current* drive happens to be instead of the intended one. The built-in `read` tool doesn't have this problem (it runs its path through `FSUtil.normalizePath()` first); `edit` never does. See `docs/lessons-learned.md` (2026-09-26 entry) for the full investigation, including the closed-without-merging upstream fix (`anomalyco/opencode#22800`, for issue `#22799`).

Rather than patch/rebuild opencode itself (this deployment installs `opencode-ai` from npm — no local build step exists to patch), this plugin hooks `tool.execute.before` for the `edit` tool only and rewrites `args.filePath` the same way opencode's own `packages/core/src/fs-util.ts` `windowsPath()` does, before the real tool runs. It mutates the `args` object's `filePath` property in place rather than reassigning `output.args` — verified against `packages/opencode/src/session/tools.ts` that `output.args` is the exact same object reference the real tool's `execute()` reads immediately afterward, so an in-place property write reaches it (a whole-object reassignment would not — see the plugin file's own header comment for the source citation, and the still-open `anomalyco/opencode#42409` that looks like the same reassignment-vs-mutation mistake).

**Scope:** `edit` only, by design for this first pass. `write` has the identical bug and `apply_patch` has an analogous one (path embedded in the patch text's `*** Update File: <path>` headers rather than a discrete field) — both left as follow-up work, see `TODO.md`.

**Deployment:** own npm package at `plugins/gitbash-edit-path-fix/` (`package.json`), same shape as `hook-logger`/`system-prompt-tools` (zero runtime dependencies beyond `@opencode-ai/plugin`'s types, erased at build time). **Not yet published to npm and not yet added to `deploy/opencode.json.example`'s `plugin` array** — it hasn't been exercised against a real opencode session on the actual Windows + Git Bash target machine yet, only unit-tested (see below and `TODO.md`).

**Tested:** `tests/unit/gitbash-edit-path-fix.test.mjs` — the `toWindowsPath()` conversion for all four Git-Bash/Cygwin/WSL path forms plus negative cases (ordinary Windows/POSIX paths, and a single-letter-prefixed-but-not-drive directory like `/cache/...` that must not be mis-caught); the hook rewriting `edit`'s `filePath` in place while leaving unrelated args untouched; the hook leaving an already-correct path alone; the hook ignoring every other tool name; the hook no-op'ing entirely off `win32` (this sandbox's own real limitation — see below); and an end-to-end reproduction of `edit.ts`'s actual `path.isAbsolute(...) ? ... : path.join(...)` line via Node's explicit `path.win32` API, showing the unpatched string stays ambiguous/driveless and the patched one resolves correctly. Driven with `process.platform` temporarily overridden to `"win32"` (a normal, configurable property on the real Node `process` object, not a mock), since this repo's Docker dev sandbox (`node:22-bookworm`) is Linux and can never actually take the `win32` branch itself — **this proves the plugin's own logic is correct, not that opencode's real Windows + Git Bash runtime honors a `tool.execute.before` argument mutation end to end.** That needs an actual run on the offline target machine, which this sandbox cannot reach.
