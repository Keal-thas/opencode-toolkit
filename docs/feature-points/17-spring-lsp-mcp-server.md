# spring-lsp mcp server

Lives in `mcp-servers/spring-lsp/`. An MCP server exposing Spring-aware code-intelligence tools — `spring_hover`, `spring_completion`, `spring_document_symbols`, `spring_workspace_symbols`, `spring_diagnostics`, `spring_boot_structure` — by spawning and driving VMware/Spring's own `spring-boot-language-server` (the LSP their "Spring Boot Tools" VS Code extension uses) over stdio, via the same `lsp-client.ts` engine `mcp-servers/java-lsp/` uses (duplicated between the two packages, not shared as a dependency — see `mcp-servers/java-lsp/README.md`'s "Design" section for why). Same `type: "remote"`/persistent-singleton shape as `java-lsp`.

Built to cover what generic Java tooling structurally can't: `@Autowired` interface fields resolving to the actual injected bean (not just the interface), `@EventListener`/`@RequestMapping` handler methods being recognized as used (jdtls's `findReferences` shows zero — they're called via reflection, not a direct source-level call), and `application.properties`/`.yml` awareness (jdtls doesn't parse these at all). `spring_boot_structure` calls the server's own non-standard `sts/spring-boot/structure` LSP extension command directly, for real bean/request-mapping info generic LSP has no equivalent of.

**Vendoring:** `spring-boot-language-server` isn't published to any package registry (confirmed against its own project's FAQ) — the only distribution channel is the VS Code extension's `.vsix`. `mcp-servers/spring-lsp/vendor/*.tar.gz` (**~81MB**, the exec jar plus the ~170-jar `lib/` its manifest's `Class-Path` requires) is committed — by a wide margin the largest binary this repo has ever committed (existing precedent, the `plugins/*/`.tgz files, are ~4KB each). `fetch-spring-boot-language-server.sh` reproduces/refreshes it from the public VS Code Marketplace.

**Tested, with an important caveat:** `mcp-servers/spring-lsp/spring-lsp.test.mjs` verifies the protocol plumbing end-to-end against the real vendored server (handshake succeeds, tarball auto-extracts, tools round-trip cleanly) — but every result in testing came back an *empty array*, not an error, because the test fixture is a bare loose `.java` file with no real Maven/Gradle project or resolved `spring-boot-starter-*` dependencies for the server to actually index. **The Spring-specific semantic richness this server exists for was not verified** — see `mcp-servers/spring-lsp/README.md`'s Status section for the two distinct reasons (no real dependencies to index; this server also expects a companion jdtls providing classpath info via a "classpath listener" mechanism that isn't wired up here) and `mcp-servers/TODO.md` for the follow-up. Also not yet wired into `./tests/run-all.sh` (same reason as `java-lsp`: no JDK 21+ in the sandbox image).
