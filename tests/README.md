# Automated tests

Covers this workspace's feature points with tests that don't require the real vLLM + Qwen model server (none of it is reachable from here anyway - see CLAUDE.md). What's covered, per top-level feature:

- **System-prompt override** (`deploy/opencode.json.example` + `deploy/system-prompt.txt`) - `unit/config-consistency.test.mjs` checks the example config is valid JSON wiring `build`/`plan`/`general` to the prompt file, that the prompt file actually differs from the untouched upstream default, and that SETUP.md's inline documentation of the same JSON doesn't drift from the real example file. `integration/docker-prompt-override.test.sh` automates the manual check previously described (but not scripted) in `docker/docker-notes.md`: spins up a throwaway container from the real dev image, wires the override the way SETUP.md instructs, and asserts `opencode debug config` actually resolves `agent.*.prompt` to `system-prompt.txt`'s exact content.
- **`system-prompt-tools.ts` plugin** (dumps the assembled prompt for manual inspection) - `unit/system-prompt-tools.test.mjs` calls its hook directly with fake `experimental.chat.system.transform` input and checks the dump file's header and content, including that each run overwrites rather than appends. Published as its own npm package (`@kealthas-dev/opencode-system-prompt-tools`), referenced by bare name (no version) exactly like `plugins/hook-logger/`/`plugins/llm-review-gate/` below - opencode's own npm-plugin loader installs it itself, see `docs/feature-points/02-system-prompt-tools-plugin.md`.
- **`hook-logger.ts` plugin** (logs every opencode hook event to JSONL) - `unit/hook-logger.test.mjs` calls several of its hooks directly and checks each hook name gets its own append-only `.jsonl` file, and that circular references in hook payloads are serialized instead of throwing.
- **`llm-review-gate.ts` plugin** (LLM safety review gating `bash` calls) - `unit/llm-review-gate.test.mjs` drives it with a fake opencode `client` (no real session, no model): ALLOW/BLOCK verdicts, non-gated tools skipped, the internal review session never reviewing its own calls, and fail-open behavior on a review error or an unparseable verdict.
- **Plugin npm-install mechanism** (`plugins/system-prompt-tools/`, `plugins/hook-logger/`, `plugins/llm-review-gate/` - each its own real published npm package, referenced by bare package name with no version, no `file:` spec, no path, see CLAUDE.md and SETUP.md steps 4/5) - verified by hand in the `docker/` sandbox with real network access: opencode's npm-plugin loader does a genuine `npm install` against the registry for a bare package name (confirmed against a stand-in real npm package before these packages were published), caching the result under `~/.cache/opencode/packages/<name>@latest/` and skipping reinstall on a warm cache. Not covered by an automated test - see `docker/docker-notes.md`'s "Plugin loading" section.
- **`toolkits/module-analysis/analyze-modules.mjs`** (batch per-module analysis driver, using `@opencode-ai/sdk` against a real opencode server) - `integration/analyze-modules.test.mjs` runs the real driver against a real opencode server (started by the SDK's `createOpencode()`) with a fake local OpenAI-compatible HTTP server standing in for the model provider, covering the happy path, a failed module leaving no output but a captured log, and the resumability/skip logic for an already-analyzed module (asserted by request count, not just by absence of a log file).
- **Shell scripts generally** (`docker/docker-entrypoint.sh`, `docs/fetch-opencode-docs.sh`) - `unit/shell-syntax.test.mjs` runs `bash -n` over all of them as a cheap regression net.
- **`mcp-servers/oracle/` (oracle MCP server)** - `mcp-servers/oracle/oracle.test.mjs` (not under `tests/unit`, so its `node_modules` resolve correctly - see the file's own header comment) spawns the real `server.js` itself as a child process (matching how a real deployment starts it independently of opencode - see `mcp-servers/oracle/README.md`'s Design section) and drives it over the real Streamable HTTP transport via `@modelcontextprotocol/sdk`'s `Client`: tool listing, a plain `SELECT`, a `CREATE TABLE`/`INSERT`/`SELECT`/`DROP TABLE` round-trip that checks a write actually survives the per-request connection closing (`autoCommit`), a query against a nonexistent table, and a regression test for a connection-failure bug found while first verifying this server by hand. Needs a real Oracle instance - the docker sandbox's `oracle` service, in its own compose project (see `docker/docker-notes.md`), which `docker/dev.sh` always brings up first, so this test can assume it's already there.
- **`mcp-servers/loki/` (loki MCP server)** - `mcp-servers/loki/loki.test.mjs`, same shape as the oracle test (spawns real `server.js`, drives it over real Streamable HTTP). Since its three tools (`loki_query_range`/`loki_labels`/`loki_label_values`) are all read-only, the test seeds its own data by pushing directly to Loki's push API rather than through the MCP server: tool listing, `loki_labels`/`loki_label_values` finding the pushed test stream, `loki_query_range` finding the pushed log line by content, an empty-result query returning cleanly, and malformed LogQL returning a clean error. Needs a real Loki instance - the docker sandbox's `loki` service, in its own compose project (see `docker/docker-notes.md`), which `docker/dev.sh` always brings up first.
- **opencode memory MCP** (the official `@modelcontextprotocol/server-memory` package, wired via `deploy/opencode.json.example`'s `mcp.memory` entry - not our own code, see `docs/feature-points/15-opencode-memory-mcp.md`) - `tests/integration/mcp-memory/memory.test.mjs` spawns the real installed package over stdio (matching how opencode itself starts a `type: "local"` server) and drives it with a real `@modelcontextprotocol/sdk` client: tool listing, a `create_entities`/`search_nodes` round-trip that also checks `MEMORY_FILE_PATH` is actually written to disk (not just held in memory), and a `delete_entities` showing up in a fresh `read_graph`. `unit/config-consistency.test.mjs` separately checks the `opencode.json.example` wiring itself (`type: "local"`, disabled by default).
- **`mcp-servers/java-lsp/`/`mcp-servers/spring-lsp/` (LSP-backed MCP servers) - NOT part of `./tests/run-all.sh`, unlike every test above.** `java-lsp.test.mjs`/`spring-lsp.test.mjs` exist and pass (spawn the real `server.js`, drive it over real Streamable HTTP, against a real `jdtls`/`spring-boot-language-server` process each), but the docker/ sandbox's image (`docker/Dockerfile`) has no JDK or jdtls installed, so they aren't wired into `tests/run-in-container.sh`. Run them manually on a machine with the right JDK/jdtls installed: `cd mcp-servers/java-lsp && npm install && node --test java-lsp.test.mjs` (needs `jdtls` on `PATH`), `cd mcp-servers/spring-lsp && npm install && node --test spring-lsp.test.mjs` (needs a JDK 21+ `java`). See both packages' READMEs' Status sections - `java-lsp`'s results are verified rich/real; `spring-lsp`'s are only verified not to crash, not to be semantically rich (needs a real Spring Boot project, not set up here).

Not covered: `docs/fetch-opencode-docs.sh`'s actual GitHub fetch (would hit the network on every test run for no real benefit - it's a docs mirror refresh, not app logic), and anything that requires the real vLLM + Qwen server, which isn't reachable from this machine at all.

## Running the tests

**Development and testing for this repo always happen inside the `docker/` sandbox, never against the host's own node/opencode install** - see CLAUDE.md. The one entry point:

```bash
./tests/run-all.sh
```

This builds the dev image if needed, then runs everything in two stages:

1. `docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh` - the unit tests (`node --test tests/unit`) and the `analyze-modules.mjs` integration test, all executed *inside* the dev container. Always go through `docker/dev.sh`, not `docker compose` directly - it isolates this worktree's Compose project from any other worktree running the sandbox at the same time (see `docker/docker-notes.md`'s "Per-worktree isolation" section).
2. `tests/integration/docker-prompt-override.test.sh` - the one script that's an exception to "everything runs in the container": it's the thing invoking `docker run` in the first place, so it necessarily runs on the host (same as every `docker compose ...` command already documented in `docker/docker-notes.md`). It touches no host node/opencode install - it starts its own disposable container with a throwaway `HOME`, so a real dev session's own config is never at risk. Everything it actually asserts on (the real `opencode debug config` resolution) still runs inside that container, not on the host.

To run just the container-side suite (e.g. while iterating, without the slower Docker-launching test):

```bash
docker/dev.sh run --rm opencode-dev bash tests/run-in-container.sh
```
