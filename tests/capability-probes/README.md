# Capability probes

Black-box probes against **opencode itself**, not this repo's code. Everything under `tests/unit/` and `tests/integration/` asserts that our own plugins/scripts/config do what they're supposed to; the scripts here instead answer "what does opencode actually do," for behavior our code depends on but that a fake-client unit test can't observe (real dispatch, real hook firing, real request bodies). Naming is the only thing that marks these as different from a real test - `*.probe.mjs`, not `*.test.mjs` - deliberately not a second framework: same plain-Node-script style as `tests/integration/analyze-modules.test.mjs`, same `createOpencode()` + fake-OpenAI-compatible-model-provider approach. None of this is wired into `tests/run-in-container.sh` or `tests/run-all.sh`, so it can never fail the suite - run a script by hand when one of its questions comes up again, or after an opencode upgrade that might have changed hook dispatch or tool schemas.

Shared scaffolding lives in `lib/harness.mjs` (fake provider + fake `HOME` + plugin loading + session/transcript helpers) and `probe-hook.js` (the one plugin every probe loads, env-var-controlled so one file covers every case instead of one plugin per script). Each script writes its raw evidence (captured request bodies, per-hook JSONL logs) to the gitignored `.local/capability-probes/<name>/` for closer inspection - the printed summary is the readable version, the evidence dir is the receipts.

```bash
cd tests/capability-probes && npm install --no-audit --no-fund   # once
docker/dev.sh run --rm opencode-dev bash -c 'cd tests/capability-probes && node hooks.probe.mjs'
```

(Same rule as everywhere else in this repo: always through `docker/dev.sh`, never against the host's own node/opencode install.)

## What each script answers

- **`hooks.probe.mjs`** - three questions about the `Hooks` interface (`@opencode-ai/plugin`) that `llm-review-gate.ts`/`hook-logger.ts` depend on:
  1. What does opencode actually send the model on a real turn? Dumped verbatim to evidence - no "expected" shape, just something to read.
  2. Which `Hooks` keys does the runtime actually invoke on a live turn vs. which are silently dead? Confirmed live: `tool.execute.before`, `chat.message`, `chat.params`, `chat.headers`, `tool.definition`, `experimental.chat.system.transform` all fire for real. `permission.ask` never fires under this probe's `bash: "allow"` tier - necessary but not sufficient proof it's dead (an `"ask"`-tier permission round-trip needs an interactive reply this headless probe doesn't attempt), consistent with `llm-review-gate.ts`'s stronger claim (checked directly against the real, currently-installed `@opencode-ai/plugin` types: `permission.ask` is a legitimate typed hook key, but `plugins.mdx`'s own "Permission Events" list only documents `permission.asked`/`permission.replied` as separate event-bus types - not this one).
  3. Does a hook's `output` mutation actually reach the real request, or does throwing/mutating only affect an isolated copy? Confirmed live for two different hooks: a throw inside `tool.execute.before` becomes the tool's real execution error (the model only ever sees the block message, never a real command result); pushing a marker string onto `experimental.chat.system.transform`'s `output.system` array shows up as its own separate system-role message in the real request (each array entry becomes its own message, not one joined string - a first pass here missed this by only checking the first system-role message and wrongly concluded the mutation was dropped).

  Also dumps every tool's real `description`/`parameters` schema as observed via `tool.definition` into evidence (`tool-definitions.json`) - the source of truth `tools.probe.mjs` uses instead of guessing tool argument shapes.

- **`tools.probe.mjs`** - drives the tools a coding agent actually uses day to day (`write`, `read`, `edit`, `glob`, `grep`, `webfetch`, `todowrite`) through a real session, using the argument shapes `hooks.probe.mjs` discovered live, and checks the *real filesystem* afterward, not just what the ToolPart claims. Confirmed live: `write`/`edit` land on disk exactly as reported (a write then an edit, verified by reading the file back independently of opencode's own report); `read`/`glob`/`grep` return real content; `webfetch` against an unreachable URL fails with a real transport error rather than silently doing nothing; `todowrite` round-trips a todo list. Also surfaced a non-obvious permission finding the hard way (first pass hung on every filesystem tool): `write` has no permission key of its own - it's gated under `edit` (per `permissions.mdx`: "`edit` — all file modifications (covers edit, write, patch)"), and any tool touching a path outside the project's own working directory needs the separate `external_directory` permission, which defaults to an `"ask"` tier that hangs forever with no TUI to answer it.

- **`permissions.probe.mjs`** - two blanket permission-tier questions, each getting its own opencode server since tiers are fixed at server startup:
  - **`"deny"`** - confirmed, but not via the mechanism you'd expect: it doesn't let the call through and reject it at execution time (that's what `tool.execute.before` throwing does) - it removes the tool from the set advertised to the model entirely. The probe's scripted fake model doesn't read the offered tool list and tries to call `bash` anyway, which is exactly what surfaces this: opencode's own "invalid tool" handling kicks in (`Model tried to call unavailable tool 'bash'`) rather than a bash-specific permission error, because as far as dispatch is concerned no such tool call was ever valid to begin with.
  - **`"ask"`** - confirmed resolvable from a headless client, no TUI needed: subscribe to `client.event.subscribe()`'s SSE stream and reply via the generated client's raw `postSessionIdPermissionsPermissionId({path:{id, permissionID}, body:{response:"once"}})` once the right event arrives. The one real trap here: the SDK's own generated types (`EventPermissionUpdated`) claim this event is called `"permission.updated"` - the live server actually emits `"permission.asked"` instead (matching `plugins.mdx`'s documented "Permission Events" list, not the `.d.ts`). Filtering on the typed name silently times out; this script filters on the real one and dumps every raw `permission.*` event into evidence so a future drift shows up as data, not another silent hang.

- **`permission-rules.probe.mjs`** - the sharper correctness question `permissions.probe.mjs` doesn't answer: does opencode's granular, pattern-based rule matching (`permissions.mdx`'s object syntax, e.g. `bash: {"*": "ask", "echo allow-me *": "allow", "echo deny-me *": "deny"}`) actually route different commands to the *right* tier, not just that each tier works somewhere in isolation? One server, one config, four commands, all four confirmed correct on the first real run: a command matching the `allow` pattern runs for real with no ask; a command matching the `deny` pattern is blocked immediately with no ask (and opencode's own error message names the exact rule that matched, unlike blanket deny - the tool stays in the model's tool list since it's still allowed for other patterns, so this is a different rejection mechanism than the blanket case); a command matching neither falls through to the wildcard `"ask"` rule and, once approved via the same event-subscribe-and-reply round trip, runs for real; the same fallthrough case replied to with `"reject"` instead blocks it just as cleanly - the model only ever sees a rejection message, never real output.

- **`gitbash-edit-path-fix.probe.mjs`** - Windows only (skips elsewhere): drives the real `edit` tool with a Git-Bash-style path (`/c/Users/...`) against the real filesystem, once without and once with `plugins/gitbash-edit-path-fix` loaded. Confirms the upstream bug exists on the machine and that the plugin makes the edit land on the intended file.

## Design notes

- **The fake provider is scripted, not a real model** (`lib/harness.mjs`'s `setPlan()`): each probe hands it an exact sequence of tool-calls/text to emit, so which tool gets called and with what arguments is fully controlled and deterministic - the point is observing opencode's own dispatch/hook behavior in response to a known input, not evaluating a model's judgment.
- **`permission: "ask"` is deliberately out of scope for the throw/block probes** - resolving an actual "ask" tier permission needs an interactive reply (`client` exposes a raw `postSessionIdPermissionsPermissionId` method for it), and getting that round-trip wrong risks a headless run hanging forever with no TUI to answer it. Where an "ask"-tier check is worth the risk, it gets its own script rather than being bolted onto an unrelated probe.
- **Evidence over assertions.** These scripts print `CONFIRMED`/`NOT CONFIRMED` against a specific claim where there is one (e.g. "the block message propagated"), but for open-ended questions ("what tools exist," "what's the exact system prompt") they just dump the raw captured data - there's no pass/fail shape to check it against, and inventing one would just be asserting our own assumption back at ourselves.
